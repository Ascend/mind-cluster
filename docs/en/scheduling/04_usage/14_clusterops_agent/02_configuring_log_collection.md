# Configuring Log Collection<a name="ZH-CN_TOPIC_00000026faultdiagnosis03"></a>

ClusterOps Agent defines which logs to collect through the **collection contract** (`collect_manifest.yaml`). The collection contract has four built-in log entities: `process_log` (CANN plog), `dl_log` (MindCluster component logs), `device_log` (device-side logs), and `host_log` (host OS logs). plog is the most commonly used log for fault locating and has the most complex configuration, so this chapter focuses on it.

## Collection Contract Example<a name="sectionfaultdiagnosismanifestexample"></a>

The core of the collection contract is the `entities` list. Each entity defines how one type of log is collected. A complete example is as follows:

```yaml
entities:
  - name: process_log            # CANN plog, container-mounted file logs
    env: ASCEND_PROCESS_LOG_PATH  # When explicitly configured in the pod spec, agent-core records it and delivers it with the collection instruction; node-collector reads it and reverse-looks up the host path
    mount_keywords: [plog]        # Fallback: scan the statically mounted shared storage first, then match mount pairs/host subdirectories, and filter by pod IP + job identifier

  - name: dl_log                 # MindCluster component logs (host path, read directly, directory structure retained)
    paths:
      - "/var/log/mindx-dl/devicePlugin"
      - "/var/log/mindx-dl/noded"
      - "/var/log/ascend-docker-runtime"
      - "/var/log/mindx-dl/volcano-scheduler"
      - "/var/log/mindx-dl/volcano-controller"
      - "/var/log/mindx-dl/npu-exporter"

  - name: device_log             # Device-side logs (generated by on-site commands)
    commands:
      - "/usr/bin/msnpureport --docker"

  - name: host_log               # Host OS logs (paths are node host paths, read directly)
    commands:
      - "dmesg -T | tail -n 100000 > dmesg"
      - "dmidecode > dmidecode.txt"
    paths:
      - "/var/log/messages*"
      - "/var/log/sysmonitor.log"
```

## Field Description<a name="sectionfaultdiagnosismanifestfields"></a>

Each entity describes the collection method through the following fields:

| Field | Description |
|---|---|
| `name` | Name of the entity, which identifies a type of log (for example, `process_log` and `dl_log`) |
| `env` | Name of an environment variable whose value points to the log directory inside the container of a job Pod (for example, `ASCEND_PROCESS_LOG_PATH`) |
| `paths` | List of log paths, specifying the log files or directories to be collected |
| `commands` | List of on-site commands, specifying the commands run on the collection node to generate log files |
| `mount_keywords` | List of fallback keywords used to locate logs by keyword: the statically mounted shared storage (/mnt/shared-storage) is scanned first, and if no hit is found, the mount pairs or host subdirectories of the job Pod are matched |

## Collection Contract Processing Logic<a name="sectionfaultdiagnosismanifestlogic"></a>

An entity can have only one of the fields configured, or several at the same time. When multiple fields are configured, Node Collector determines the actual collection method to be executed based on the following priorities.

| Priority | Field | Processing Logic |
|---|---|---|
| 1 | `env` | Environment variable. While the Pod is alive, Agent Core records the `env` value and all `hostPath` mount pairs into the central mount relationship table and delivers them with the Pod list in the TriggerCollect collection instruction. Node Collector reads the `env` value (in-container path), reverse-looks up the host path through the mount pair, and collects logs from the host. When `env` collection succeeds, `paths`, `commands`, and `mount_keywords` are not executed. When `env` is not recorded or the reverse lookup fails, the lower-priority fields continue to be processed |
| 2 | `paths` / `commands` | Fields at the same level, which are both executed when `env` is not configured or collection fails. `paths` preferentially matches the mount pair of the job Pod by in-container path, reverse-looks up the host path, and then copies files (directory structure retained). If the job Pod has no matching mount pair, the configured path is read directly as a host path. The `dl_log` and `host_log` entities are special cases: their `paths` are always read directly as host paths without matching the mount pairs of the job Pod. `commands` runs commands in a temporary directory to generate files and copies them to the collection directory. The entire command string must exactly match the trustlist; otherwise, execution is refused |
| 3 | `mount_keywords` | Keyword fallback. It is executed only when `paths` is not configured. The **statically mounted shared storage** is scanned first (`/mnt/shared-storage`; the protocol is not restricted, such as NFS, CephFS, or cloud disks, and it is mounted by the deployer), and the Pod IP and job identifier (`MINDX_TASK_ID`) are used to filter out the log subdirectory belonging to the Pod. The scan ends at the first hit. If no hit is found in the shared storage, all mount pairs of the job Pod are matched by keyword (a hit occurs when the host or container path contains the keyword). If there is no direct hit, the subdirectories of the mounted host path are scanned |

> [!NOTE]
>
> - The priority of collection fields is `env` > `paths` = `commands` > `mount_keywords`. When a higher-priority field is configured and collection succeeds, lower-priority fields are not executed. `paths` and `commands` are at the same level, and both are executed when env is not configured or collection fails.
> - The shared storage scan of `mount_keywords` does not depend on a fixed directory structure. A directory name **only needs to contain any of the keywords** (`mount_keywords` uses substring matching, and the default `plog` can hit `plog`, `plogs`, `plog_xxx`, and so on); it is not limited to `plogs` in the example. In addition, two levels of dynamic segments, the job identifier and the Pod IP, are used for filtering (both layouts `alllogs/<task_id>/plogs/<ip>` and `alllogs/<ip>/plogs/<task_id>` are supported, and the order of dynamic segments is not fixed), so that only logs belonging to this job and this Pod are collected and logs of other jobs on the same shared storage are not collected. After the first hit in the shared storage, the scan ends and host mount directories are no longer matched. After a job Pod is deleted (the kubelet volume mount point disappears accordingly), the shared storage mount point is still mounted on Node Collector, so collection can still be completed.

## Log Entity Configurations<a name="sectionfaultdiagnosistentities"></a>

### process_log (CANN Plog)<a name="sectionfaultdiagnosisplog"></a>

CANN plog is the runtime log of training or inference processes. It contains key error information such as Ascend operator and communication errors and is the preferred log for fault locating. The default configuration of the `process_log` entity in the collection contract is as follows:

```yaml
entities:
  - name: process_log            # CANN plog, container-mounted file logs
    env: ASCEND_PROCESS_LOG_PATH  # When explicitly configured in the pod spec, agent-core records it and delivers it with the collection instruction; node-collector reads it and reverse-looks up the host path
    mount_keywords: [plog]        # Fallback: scan the statically mounted shared storage first, then match mount pairs/host subdirectories, and filter by MINDX_TASK_ID + pod IP
```

The plog entity has two fields configured, `env` and `mount_keywords`. During collection, plogs are located as follows:

1. **env (preferred)**: Used when the job Pod explicitly configures `ASCEND_PROCESS_LOG_PATH` in the Pod spec. Agent Core records the literal env value and all hostPath mount pairs of the Pod into the central mount relationship table (retained within the TTL and still available after the Pod is deleted) and delivers them with the Pod list to Node Collector on the corresponding node in the TriggerCollect collection instruction. Node Collector reads the env value (in-container path), reverse-looks up the host path through the mount pair, and then reads plogs from the host.
2. **mount_keywords (fallback)**: When `env` is not recorded or the reverse lookup fails (for example, `ASCEND_PROCESS_LOG_PATH` is exported by the startup script and is not in the Pod spec), Node Collector matches in sequence according to `mount_keywords` (`plog`): the **statically mounted shared storage** is scanned first (`/mnt/shared-storage`, and the scan ends at the first hit); if no hit is found, the mount pairs of the job Pod and the subdirectories of the mounted host path are matched. In the shared storage scan, the Pod IP and job identifier (`MINDX_TASK_ID`) are used to filter out the plog subdirectory belonging to the Pod. A directory name only needs to contain the keyword (substring matching; `plog` can hit `plog`, `plogs`, `plog_xxx`, and so on). The matching does not depend on a fixed directory structure and is compatible with both layouts `alllogs/<task_id>/plogs/<ip>` and `alllogs/<ip>/plogs/<task_id>` (the order of dynamic segments is not fixed), and logs of other jobs on the same shared storage are not collected. This scan order is the same for all entities (shared storage first for both plog and non-plog entities).

#### Configuring Plog Output<a name="sectionfaultdiagnosisplogtask"></a>

Whether plog can be collected depends on how the plog output directory is mounted, which corresponds to two scenarios:

- **hostPath mode (env reverse lookup)**: The job Pod mounts the plog directory to the host through `hostPath` and sets `ASCEND_PROCESS_LOG_PATH` in the Pod spec. The `pathmap` of Agent Core records the `hostPath` mount pair, and Node Collector collects logs by reverse-looking up the host path through env.
- **Shared storage mode (static shared storage mount for mount_keywords)**: The job Pod mounts the path where the plog directory resides through a shared storage volume (the protocol is not restricted, such as NFS, CephFS, or cloud disks, for example, `/job/code`), and `ASCEND_PROCESS_LOG_PATH` is dynamically injected by the startup script (for example, `/job/code/alllogs/$MINDX_TASK_ID/plogs/$XDL_IP`). During deployment, the shared storage is statically mounted to `/mnt/shared-storage` of Node Collector, and the `mount_keywords` fallback of Node Collector uses `MINDX_TASK_ID` and the Pod IP under the mount point to filter out the plog directory of the Pod. The shared storage is mounted by kubelet/CSI and read directly by Node Collector without the mount command, so collection is still possible after the job Pod is deleted.

The following uses `hostPath` mode as an example. Key segments of the AscendJob Pod template are as follows:

```yaml
apiVersion: mindxdl.gitee.com/v1
kind: AscendJob
metadata:
  name: job-x
  namespace: training
spec:
  tasks:
  - template:
      spec:
        containers:
        - name: main
          image: <training_image>
          env:
          - name: ASCEND_PROCESS_LOG_PATH   # Specify the plog log directory in the container
            value: /home/ascend/log
          volumeMounts:
          - name: plog
            mountPath: /home/ascend/log     # Consistent with ASCEND_PROCESS_LOG_PATH
        volumes:
        - name: plog
          hostPath:
            path: /data/plog               # Plog host directory (must be created on the node in advance)
            type: Directory
```

The mapping between this job YAML and the collection contract is as follows:

1. `ASCEND_PROCESS_LOG_PATH=/home/ascend/log` in `env`: Node Collector reverse-looks up the host path `/data/plog` accordingly and completes collection of the plog entity.
2. `volumeMounts.mountPath` (`/home/ascend/log`) must be consistent with `ASCEND_PROCESS_LOG_PATH`; otherwise, the `env` reverse lookup cannot hit the mount pair.
3. `volumes.hostPath.path` (`/data/plog`) is the actual plog directory on the host, from which Node Collector finally reads logs.

> [!CAUTION]
> The host path of the plog directory of the job Pod must exist; otherwise, the Pod fails to be scheduled. The host directory must be created by the user in advance, and the deployment manifest does not create directories automatically.

The following uses shared storage mode as an example. The job Pod mounts the path where plog resides through a shared storage volume (the protocol is not restricted, such as NFS, CephFS, or cloud disks; `ASCEND_PROCESS_LOG_PATH` is dynamically concatenated by the startup script based on `MINDX_TASK_ID`/`XDL_IP`, and the plog directory path on the shared storage is not fixed, so both layouts can be matched):

```yaml
apiVersion: mindxdl.gitee.com/v1
kind: AscendJob
metadata:
  name: job-x
  namespace: training
spec:
  tasks:
  - template:
      spec:
        containers:
        - name: main
          image: <training_image>
          env:
          - name: MINDX_TASK_ID            # Job identifier (dynamic ID, recorded by Agent Core, used for shared storage scan filtering)
            value: task-42
          # ASCEND_PROCESS_LOG_PATH is dynamically injected by the startup script and is not in the Pod spec:
          #   export ASCEND_PROCESS_LOG_PATH=/job/code/alllogs/$MINDX_TASK_ID/plogs/$XDL_IP
          volumeMounts:
          - name: code
            mountPath: /job/code          # Container mount path of the shared storage volume (mount_path)
        volumes:
        - name: code
          nfs:                             # Shared storage volume; the protocol is not restricted (NFS, CephFS, cloud disks, and so on)
            server: 10.0.0.9              # NFS server (server)
            path: /export/code            # NFS export path (path)
```

The plog directory path on the shared storage contains two levels of **dynamic IDs**, whose order is not fixed. Both layouts can be hit (the plog directory name is not limited to `plogs`; any directory containing the keyword `plog`, such as `plog` and `plog_xxx`, is acceptable):

| Dynamic ID | Source | Purpose |
|---|---|---|
| `MINDX_TASK_ID` (for example, `task-42`) | Job Pod environment variable | Filters out log directories of other jobs on the same shared storage |
| pod IP (for example, `10.0.0.5`) | Job Pod status | Filters out log subdirectories of other Pods of the same job |

```text
# Layout 1: task_id before pod_ip
/job/code/alllogs/task-42/plogs/10.0.0.5/   # Hit: the path contains task_id, and the name of the subdirectory under plogs == pod_ip
/job/code/alllogs/task-99/plogs/9.9.9.9/    # Skipped: plog of another job (task-99)

# Layout 2: pod_ip before task_id
/job/code/alllogs/10.0.0.5/plogs/task-42/   # Hit: the path contains pod_ip, and the entire plogs directory is taken
/job/code/alllogs/9.9.9.9/plogs/task-99/    # Skipped: plog of another Pod (9.9.9.9)

# Directory name variants (plogs is only an example; any name containing the keyword plog is acceptable, such as plog or plog_2026):
/job/code/alllogs/task-42/plog/10.0.0.5/    # Also a hit
```

The mapping between this job YAML and the collection contract is as follows:

1. Agent Core records the literal env value of the Pod (including `MINDX_TASK_ID`) and the pod IP and delivers them to Node Collector with the collection instruction. The pathmap does not record the mount information of the shared storage volume (server/path/mount_path).
2. `ASCEND_PROCESS_LOG_PATH` is injected by the startup script (and is not in the Pod spec). After the env reverse lookup fails, the `mount_keywords` fallback is used.
3. Node Collector matches plog directories by the keyword `plog` under the statically mounted shared storage (`/mnt/shared-storage`) and then filters out the plog directory of this Pod using `MINDX_TASK_ID` (`task-42`) and the Pod IP (for example, `10.0.0.5`) before collection.

After the job Pod is deleted, the kubelet volume mount point disappears accordingly, but the shared storage mount point is still mounted on Node Collector, so collection can still be completed without affecting diagnosis.

#### Mounting the Plog Host Directory to Node Collector<a name="sectionfaultdiagnosisplogmount"></a>

Node Collector is a DaemonSet independent of job Pods and runs on each NPU node. It reads host logs through `hostPath` mounts. By default, Node Collector has mounted the following host directories:

- `/var/log` (system logs)
- `/usr/local/Ascend` (full Ascend directory)
- `/usr/local/dcmi`
- `/usr/bin/msnpureport` (single file)

> [!IMPORTANT]
> **The shared storage must be statically mounted to `/mnt/shared-storage` of Node Collector.** If shared logs such as job plogs are stored on the shared storage (NFS, CephFS, cloud disks, and so on; the protocol is not restricted), the shared storage must be mounted to `/mnt/shared-storage` of Node Collector; otherwise, plogs on the shared storage cannot be collected. The shared storage is mounted by kubelet/CSI (see the commented `shared-storage` example in `node-collector.yaml`; fill in the `nfs` or `csi` parameters according to the actual protocol of the cluster and uncomment them to enable the configuration), and Node Collector reads the mount point directly (so collection is still possible after the job Pod is deleted).
> [!CAUTION]
> **The plog host address must be mounted in node-collector.yaml.** If the plog host directory of the job Pod is not within the existing mount scope of Node Collector (for example, `/data/plog` in the example above), Node Collector cannot read the plog directory from the host, causing plog collection to fail. In this case, you must add a `hostPath` mount for the host directory in `node-collector.yaml`.

The following uses mounting `/data/plog` as an example. Add the following configuration to `volumeMounts` and `volumes` in `node-collector.yaml` respectively:

```yaml
        volumeMounts:
        - name: plog
          mountPath: /data/plog            # Consistent with the host path
          readOnly: true
      volumes:
      - name: plog
        hostPath:
          path: /data/plog                # Plog host directory (must be created on the node in advance)
          type: Directory
```

After the modification, apply the manifest again and perform a rolling update of the DaemonSet:

```shell
kubectl apply -f node-collector.yaml
kubectl rollout restart daemonset node-collector -n mindx-dl
```

### dl_log (MindCluster Component Logs)<a name="sectionfaultdiagnosisdllog"></a>

The `dl_log` entity collects the runtime logs of MindCluster components (such as Ascend Device Plugin, NodeD, Ascend Docker Runtime, Volcano, and NPU Exporter). The default configuration is as follows:

```yaml
  - name: dl_log                 # MindCluster component logs (host path, read directly, directory structure retained)
    paths:
      - "/var/log/mindx-dl/devicePlugin"
      - "/var/log/mindx-dl/noded"
      - "/var/log/ascend-docker-runtime"
      - "/var/log/mindx-dl/volcano-scheduler"
      - "/var/log/mindx-dl/volcano-controller"
      - "/var/log/mindx-dl/npu-exporter"
```

The `dl_log` entity has the `paths` field configured. Node Collector **reads the configured paths directly as host paths** and copies files (directory structure retained), without matching the mount pairs of job Pods.

### device_log (Device-Side Logs)<a name="sectionfaultdiagnosisdevicelog"></a>

The `device_log` entity collects Ascend device-side logs, which are generated by on-site commands. The default configuration is as follows:

```yaml
  - name: device_log             # Device-side logs (generated by on-site commands)
    commands:
      - "/usr/bin/msnpureport --docker"
```

The `device_log` entity has the `commands` field configured. Node Collector runs trustlist commands in a temporary directory to generate log files and copies them to the collection directory. The command string must exactly match the trustlist; a tampered command string is refused.

### host_log (Host OS Logs)<a name="sectionfaultdiagnosishostlog"></a>

The `host_log` entity collects OS logs of node hosts (such as kernel logs and system monitoring logs). The default configuration is as follows:

```yaml
  - name: host_log               # Host OS logs (paths are node host paths, read directly)
    commands:
      - "dmesg -T | tail -n 100000 > dmesg"
      - "dmidecode > dmidecode.txt"
    paths:
      - "/var/log/messages*"
      - "/var/log/sysmonitor.log"
```

The `host_log` entity reads node host paths (`paths`) directly and runs on-site commands (`commands`).

## Updating the Collection Contract<a name="sectionfaultdiagnosismanifest"></a>

The collection contract (`collect_manifest.yaml`) is built into the image by default and located at `/home/hwMindX/collect_manifest.yaml`. If you need to adjust collection items on site (add entities, modify `env`, adjust keywords, and so on), you do not need to rebuild the image or restart Node Collector. Instead, write the collection contract to the cluster ConfigMap directly through Kubectl Plugin.

```shell
kubectl ascend_diag --collect-manifest ./collect_manifest.yaml
```

After the command is executed successfully, the output is as follows:

```text
collect manifest written to ConfigMap collect-manifest/cluster-system: ./collect_manifest.yaml
subsequent diagnostics will use the updated collect manifest (node-collector re-reads this CM on every collection, no restart needed)
```

> [!NOTE]
>
> - The collection contract ConfigMap resides in the `cluster-system` namespace. Running the command requires that the current kubeconfig have the create/apply permission on this ConfigMap.
> - Node Collector re-reads the ConfigMap `collect-manifest` on every collection, so the update takes effect immediately without a restart.

## Notes<a name="sectionfaultdiagnosisnotes"></a>

- **Different jobs outputting to the same directory may cause inaccurate diagnosis**: If multiple jobs output logs to the same host directory (for example, multiple jobs share the same plog mount directory), Node Collector collects all logs in that directory based on the mount pairs of the job Pods. Logs of different jobs are mixed together, which may cause the diagnosis result to locate the wrong job. You are advised to use an independent log directory for each job.
- **Failure to collect logs does not affect diagnosis success**: If a job does not generate log output (for example, the process is not started or the log path is not mounted) or Node Collector cannot collect logs, the diagnosis process is still executed normally and generates a report. However, the lack of the corresponding logs reduces diagnosis accuracy. You can check the log collection status through the diagnosis report or Node Collector logs.

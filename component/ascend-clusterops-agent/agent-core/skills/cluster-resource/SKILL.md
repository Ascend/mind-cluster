# 集群资源查询

## 什么时候用

- 按节点看资源账目：CPU（核）与各整卡资源桶（张）的容量、可分配、已用、空闲，以及独立的故障/隔离卡数。
- 典型问法："集群还有多少空闲卡？""哪个节点能再起一个任务？""为什么可分配比总量少？"
- 只读查询。具体哪张卡坏了用 `faulty-device`；哪张卡被隔离用 `isolated-device`。本工具不提供芯片实时利用率。

## 调用工具与参数

工具名 `cluster_resource`（下划线）。参数只有 `node` 一个：

| 参数 | 类型 | 规则 |
|---|---|---|
| `node` | 字符串数组，可选 | 省略或 null = 不限定节点（全量读取）；传数组 = 只看这些节点；传空数组 `[]` = 显式空范围（不读来源，直接返回空 `data.node`）。一律传数组（单个字符串也会被服务端归一为单元素数组，公网 CLI 单值形态由此兼容） |

```json
{}
```

```json
{"node": ["node-1", "node-2"]}
```

## 返回字段与解读

**返回是工具层原始信封 JSON**，不经过任何摘要或改写：`request_id`、`tool`、`status`、`elapsed_ms`、`data`、`errors[]`。下面的字段路径就是 JSON 里的实际路径，直接用路径引用，不要把整段 JSON 贴给用户。返回超过长度上限时末尾会带一句「已截断」声明：被截断的部分没有输出，不代表为空或不存在，需要完整数据请缩小 `node` 范围或改用 kubectl 查询，并把这一点写进结论。

数据入口 `data.node{}`：按节点名索引的字典（`{}` 是节点名占位），**只有逐节点明细，没有跨节点汇总**。每个节点对象两类键并列：

- `data.node{}.cpu`：CPU 账目，单位是**核**（浮点数）：`capacity_cores`、`allocatable_cores`、`used_cores`、`idle_cores`。
- 资源桶：与 `cpu` 同级的动态键，**桶名来自返回键（如 `Ascend910`、`npu`），不要写死**；每个桶单位是**张**（整数）：`capacity`、`allocatable`、`used`、`idle`、`fault`、`isolated`。同一节点两个桶并存时各自独立，不互相替代、不合并。

解读要点：

- **单位分清**：`cpu` 是核（浮点），资源桶是张（整数）。
- **`used` 只统计 Running 容器的 requests**（普通容器、requests 口径；非 Running、init 容器、limits 都不算），是"请求占用"不是利用率；`idle` = 可分配减已用，负数原样保留。
- **`fault` 与 `isolated` 是独立计数**：分别来自设备故障事实与 ClusterD 隔离名单两套来源，各自去重、互不扣减；同一张卡可以同时计入两者，也不能相加。
- **null 表示未知，不是 0**：`capacity` / `allocatable` / `idle` / `fault` / `isolated` 都可能为 null（来源不可读）；`used` 恒有值，0 表示没有匹配请求。
- **没有跨节点汇总**：要报集群总量必须自己把各节点相加，并声明是派生值（**由明细求和**）。含 `null` 字段的节点不可计入求和：跳过并在结论里声明覆盖范围（如"X 个节点共…，另有 Y 个节点数值未知"），不得把 `null` 当 0；"容量减可分配"的差值也不等于故障或隔离数。
- 无整卡资源键的节点不出现。点名节点的解读以 `status` 为准：**`ok` 下**未出现的点名节点 = 确认无 NPU 资源（ok 保证全部点名节点都已读到，缺即无键）；**`partial` 下**未出现 = 未能读取或不存在（按缺口声明，见下）——两种情形不得混读。

## 无数据与异常提示

- 外层 `status` 是**查询质量**而非集群健康：`ok` 说明本次结果完整；`partial` 说明只查到一部分——先给已观察到的结果，再说缺口。**缺口分两层**：已列出节点的 `null` 字段就是该来源不可读（按上方 null 规则声明覆盖范围）；点名了却未出现在 `data.node` 中的节点 = 未能读取或不存在（返回中不可见，凭 `request_id` 查服务端日志）；`error` 说明执行失败（`data` 为 null，按 `errors[].code` 说明原因，不要回答"资源充足/一切正常"）。
- `errors[]` 只承载执行失败（`INVALID_ARGUMENT` / `TOOL_NOT_FOUND` / `INTERNAL_ERROR`），条目含 `code` 与 `message`，`retryable` 恒为 `false`，不要据此自动重试。
- 仅 `status=ok` 时数字才可读作"该节点当前确实如此"；`partial` 下已给数字只是已观察口径。
- 只读技能：不执行任何变更操作；需要动作时引导用户走命令行或变更流程。

## 回答格式（三段式，缺一不可）

1. **总结**：1~3 句直接回答，先给结论（还有多少可用、瓶颈在哪个节点/哪个桶）。
2. **依据**：逐条列出结论出处，写清工具名与字段路径（如 `cluster_resource` → `data.node{}.cpu.idle_cores`），合计值必须标注「由明细求和」，数值必须与返回一致。
3. **说明与建议**：先交代本次缺口与限制（`partial`、截断、null 字段与无法求和的节点、桶名动态），再给下一步建议（查具体故障卡用 `faulty_device`、查隔离用 `isolated_device`）。

三段都要写，也不要把整段信封 JSON 贴给用户。

## 禁止事项

- 不编造返回里没有的字段或计数，不虚构跨节点总数；空结果不等于集群健康。
- 不把技能名当工具名：工具名必须是 `cluster_resource`（本技能名是 `cluster-resource`）。
- 不跨技能臆测：设备故障查 `faulty_device`，隔离名单查 `isolated_device`，资源查 `cluster_resource`，任务状态查 `task_status`，任务日志诊断查 `diagnose`。

契约依据：`agent-core/tools/builtin.py`（工具注册）、`query_schemas.py`（入参与返回模型）。

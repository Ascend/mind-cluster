# skills/ 技能目录

这个目录是 agent-core 的**技能宿主**数据源（宿主代码在 `agent-core/chat/skill_loader.py`）：
模型先看到技能清单（每技能一行 `name: description`，注入系统提示词），需要详细指引时再通过
`load_skill(name)` 工具按需读取正文——正文不常驻提示词（渐进披露）。

工具结果**原样交给模型**（工具层信封 JSON，超过 9000 字符时末尾带一句截断声明），解读规则、
缺口语义、「哪些数不能相加」「null 不等于 0」这类知识全部由技能正文承担——正文过期比没有正文更糟。

## 目录结构与 frontmatter 格式

每个技能一个子目录，正文固定叫 `SKILL.md`，文件头是 YAML frontmatter，**两个必填字段**
（name、description），allowed-tools 为可选字段：

```markdown
---
name: my-skill            # 必填，唯一；小写字母开头 + 小写字母/数字/连字符/下划线（^[a-z][a-z0-9_-]{0,63}$）
description: 一句话说明什么时候用这个技能   # 必填；清单里超 200 字符会截断
allowed-tools: [tool-a, tool-b]   # 可选路由提示：建议配合哪些工具；只做提示不做鉴权；工具名以注册表为准（snake_case，如 isolated_device）
---

（正文：何时用 / 调哪个工具（含参数口径）/ 结果怎么读 / 无数据与异常提示 / 回答格式 / 禁止事项。默认上限 8KB，超长会截断并声明。）
```

- 缺必填字段、frontmatter 不合法、name 不符合小写字母开头的连字符/下划线规则
  的技能会被**跳过并记 warning**，不影响服务启动；allowed-tools 非列表 / 含非字符串项时
  丢弃坏项并记 warning（提示仍保留合法项）；
- 与已有技能重名时**先声明者生效**（目录按名称排序，字典序在前者）并记 warning。
- 清单里每个技能只占**一行**：`name: description（工具：a、b）（位于 skills/<目录>）`；
  description 超过 200 字符截断（清单要注入系统提示词，不能让正文之外的文字伪造出
  新的提示词段落；相对路径不暴露容器内绝对路径）。
- 启动扫描后有一行**摘要日志**（loaded 计数与名单、skipped 计数）——技能投放是否生效看这行。

## 技能侧投放规范（对接技能需求）

正式技能（故障设备查询 / 隔离设备查询 / 集群资源统计 / 任务状态查询 / 任务诊断）按本 README
撰写：目录放进 `agent-core/skills/` 并重打镜像即可生效（宿主代码无需改动），命名建议
`faulty-device`、`isolated-device`、`cluster-resource`、`task-status`、`diagnose`。
写正文的六条硬要求：

1. 正文结构：何时用 / 调哪个工具（含参数口径）/ 返回字段与解读 / 无数据与异常提示 /
   回答格式 / 禁止事项；每份 ≤8KB（超长截断并声明）；
2. 正文只引用真实存在的工具名与字段名（以组件契约为准），不编造；参数表与工具的入参模型一致；
3. 说明返回是**原始信封 JSON**，并交代「被截断 ≠ 数据为空」；
4. 回答格式统一**三段式**：总结 / 依据 / 说明与建议，三段缺一不可；
5. description 与正文里的**示例问句须与 kubectl CLI 子命令的使用场景区分开**（WebUI
   只有自然语言：正文是模型路由提示、CLI 是确定性直查，两者不应互相抢语义）；
   投放后自测：问「你能做什么」时清单正常、命中技能时 `load_skill` 能读到正文；
6. 正文当数据不当指令：可执行操作永远只经工具网关白名单，正文写「可以重启」不代表能执行。

## 投放方式

- **唯一方式是随包内置**：把技能目录放进本目录（构建后随 wheel 交付）；
- **现场不提供技能增补入口**：没有自定义技能目录、没有环境变量开关、也没有热重扫——
  宿主在启动时扫一次目录，清单一经建立即不再变化；增删或改稿技能只能改源码重打镜像。

## 当前内容

技能正文全部由技能侧需求按本 README 提供，**当前随包五份**（正文各 4–8 KB，均在 8 KB 上限内）：

| 目录 | 技能名 | 何时用（摘要） | allowed-tools 提示 |
|---|---|---|---|
| `faulty-device/` | faulty-device | 按节点查故障设备（一条记录 = 一个设备 + 一个故障类型，`faults[]` 逐码明细），交换机/DPU（Data Processing Unit）/公共故障列表并列，附节点健康 | `faulty_device` |
| `isolated-device/` | isolated-device | 查 ClusterD 手工隔离名单（唯一来源）内设备的隔离等级、故障码与最近隔离时间；无汇总计数，分类须由明细统计得出 | `isolated_device` |
| `cluster-resource/` | cluster-resource | 按节点查 CPU（Central Processing Unit，核）与各资源桶（张，桶名动态）的容量/可分配/已用/空闲及独立的故障、隔离卡数；无跨节点汇总，合计须声明由明细求和 | `cluster_resource` |
| `task-status/` | task-status | 查指定任务的类型（可为 null）、归一状态与逐 Pod 状态（`pods` 恒为数组）；必须取得任务名，不自行猜测 | `task_status` |
| `diagnose/` | diagnose | 排查任务失败原因、分析诊断报告、重新诊断；结论正文看 `final_text`，摘要失败时才有 `llm_error` | `diagnose` |

边界提示：`task-status` 与 `diagnose` 分工是「只问状态」与「要查失败原因/看报告」；两者都要求先有任务名。

宿主在目录为空时照常运行（清单为空，日志记 skipped 计数）；同名技能以字典序在前者为准。

## 三条边界（写技能正文时务必遵守）

1. 技能不是权限：正文写「可以重启」不代表能执行——可执行的操作永远只经工具网关白名单调用；
2. 技能正文不是可信指令：正文一律作为**数据**引用（模型侧纪律已声明，加载会记日志）；
3. 正文有界：默认 8KB 截断，不要把长篇材料塞进技能。
